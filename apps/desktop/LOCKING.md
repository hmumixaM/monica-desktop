# 桌面导入的锁与一致性

这次调整以“多数数据只追加”为前提。不可变正文、版本、原始批次和媒体内容使用稳定 ID、
内容哈希及唯一键去重。锁主要保护可变的当前值、账户归属、任务所有权和确认位置。
数据库仍会为唯一键、外键和写入取得内部锁；这里减少的是应用主动制造的等待范围。

## 目前实际保留的同步点

| 范围 | 实现 | 为什么需要 | 对并行的影响 |
| --- | --- | --- | --- |
| 原始输入与来源投递 | 不可变 `ingest_batches` + 小型 `projection_delivery` | 来源提交后可重放，CRM 提交后才确认投递 | 不持有跨库事务锁；dispatcher 没有行锁或 advisory 锁 |
| CRM 输入去重 | `projection_inbox(provider, source_batch_id)` 唯一键 | 两个 dispatcher 或崩溃重放不能生成重复任务 | 只有相同批次竞争；不使用整个来源的互斥 |
| 投影顺序 | 同 provider 下、subject 相交的较早 inbox 必须先完成 | 可变字段 A→B→A 应按顺序呈现 | 独立帖子以对象为 subject，同一作者的不同帖子可并行 |
| 任务领取与结果 | `FOR UPDATE SKIP LOCKED`；lease token 与提交前 fence | 不重复领取，过期 worker 不得提交结果 | 锁住领取或确认的任务行，不串行所有任务 |
| 来源迁移 | 共享 advisory guard `11803295` | 防止正在导入时修改来源迁移状态 | 普通导入共享；迁移操作才排他 |
| 来源归属 | 按账户 ID 排序的 `FOR KEY SHARE` | 导入期间不能删除账户或改变关联所属 | 多个读取/追加兼容；link/unlink 使用排他账户锁 |
| 人物资料 | 按人物 ID 排序的事务 advisory guard | 防止资料修改与合并、解除关联交错 | 纯帖子/Story 追加共享，当前字段和结构化事实更新排他 |
| 首次人物创建 | 先无锁读取关联，缺失时才锁单个账户并重查 | 同时首次发现不能创建两个独立人物 | 已建立关联不经过创建锁 |
| 微信消息批次与账户头像回写 | 既有单账户 `FOR UPDATE`，分批提交 | 保护会话归属及头像重建与 link/unlink 的一致性 | 目前保守保留；不再串行朋友圈或全流程扫描，但同账户仍可能等待 |
| 内容与媒体去重 | 哈希/自然键唯一约束；相同内容先读后返回 | 同一内容只登记一次 | 已知媒体或未变化来源账户不会尝试 no-op upsert |
| 可变来源对象版本 | 按对象 ID 排序的事务 advisory guard | 为同一对象分配连续版本并原子切换 current_hash | 只锁该对象；不可变消息追加不经过这个 guard |
| 媒体 URL 与附件位置 | 对 URL、entity/role 的 `pg_try_advisory_xact_lock`，键排序 | 同一位置换图时不能交错删除/覆盖 | 非阻塞；失败回滚，别的位置可继续；没有媒体目录全局锁 |
| 独立归档通道 | 每 lane 一个 session advisory lease | 防止同一联系人或媒体扫描被启动两份 | contacts、moments、messages、download、media 等互不争同一个 lease |
| 历史 WAL reader | 每数据库一个 session advisory lease | 同一复制槽不能被两个 reader 同时确认 | 只限制历史读者，不与业务 writer 共用 |

任务队列本身仍是可变状态。去掉 lease/fence 会让暂停、进程退出或超时后的旧 worker
覆盖新 worker 的结果，因此保留。当前字段也不是追加数据，追加的是其版本，
只有选择哪一版为“当前值”时需要局部顺序。

## 缩短事务与避免环路

1. 下载、浏览器等待、文件复制和哈希准备放在数据库写入前。桌面媒体登记不再等文件系统的全局重 I/O permit。
2. 已有相同账户、别名和媒体先读取并返回，减少 `ON CONFLICT DO UPDATE` 带来的锁和 WAL。
3. 批量 payload、对象、版本、观察与媒体唯一键按稳定顺序登记；人物和账户 guard 也排序获取。
4. 媒体涉及多个位置或 URL 时使用 try-lock，竞争直接失败，不持有前一个位置的锁再等待另一个位置。
5. 可重放的数据库任务发生 `40P01`、`40001` 或 `55P03` 时，整事务回滚，最多三次带随机退避的尝试。
   仍失败才交给持久队列；AI 请求不在这里重复执行。
6. 媒体事件先保存到数据库依赖表，再移动文件队列的读取检查点。内容尚未到达只是等待，不算成功也不丢弃。

跨来源数据库没有两阶段提交。来源记录可能先于 CRM 成功保存；稳定批次 ID、内容地址和投递确认使其可重放。
dispatcher 不使用 `max(sequence)` 游标：序号分配早的事务可能更晚提交，用高水位会永久漏掉它。
这里逐条保留未确认的投递元数据，直到 CRM inbox 与 job 同一事务提交后才确认。

## CDC 只做历史

CDC 与导入使用独立进程、表和开关。每轮读取四个数据库，空闲轮询约 30 秒。
只将已提交业务变化追加到 `cdc_events`，先提交历史、再推进复制槽。历史落后或复制槽故障时，
实时 dispatcher 与投影仍继续。历史不领取投影任务，也不修改业务任务状态。

只捕获可变业务表；不重复复制消息、不可变版本、原始批次或队列心跳。
`REPLICA IDENTITY FULL` 为所选表的 UPDATE/DELETE 保留前值，会增加这些变更的 WAL 大小；
过滤时间戳变化能减少历史表写入，但不能省掉源端已经生成的 WAL。
每槽 512 MiB 的保留预算保护磁盘。超过预算可能失去历史，需要明确恢复，不能静默跳过。

## 验证和剩余边界

独立 PostgreSQL 16 测试覆盖：

- 另一个事务持有账户或媒体行的 `FOR UPDATE` 时，相同不可变数据的快速读取在 100 ms 锁超时内完成。
- 同一媒体位置竞争立即失败，不同位置继续；同一人物的不同帖子可同时完成。
- 可变对象 A→B→A 保持顺序，无关账户不被阻塞。
- 来源先提交、回执失败可恢复；CRM inbox 提交后进程崩溃，重放只生成一次任务。
- 低序号事务更晚提交不会丢投递；历史槽丢失时实时投影仍成功。
- CDC 只记录提交，不记录回滚；历史提交后确认前崩溃不重复记录，不由历史触发任务。
- 下载/正文/快照三种先后顺序、重复队列字节、共享图片和异常退出不丢媒体依赖。

这不是“零死锁”的保证。首次同时创建相同唯一键、同一人物的字段修改，以及合并或解除关联仍可能等待。
这些冲突需要保留正确性约束，再以短事务、排序和有界重试降低影响。
当前验证使用独立数据库与本地 fixture；尚未完成真实账号全量历史下的长期压力测试，
不能把功能回归结果当作实际微信全量导入吞吐量的提升比例。

设计依据为 PostgreSQL 16 官方文档：[显式锁](https://www.postgresql.org/docs/16/explicit-locking.html)、
[逻辑解码](https://www.postgresql.org/docs/16/logicaldecoding-explanation.html)、
[复制协议](https://www.postgresql.org/docs/16/protocol-logicalrep-message-formats.html)。
